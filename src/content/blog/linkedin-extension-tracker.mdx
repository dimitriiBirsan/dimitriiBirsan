This investigation started with some odd-looking requests in the browser’s developer tools: why was LinkedIn trying to load resources from Chrome extensions?

I followed the requests back to the code that made them. These are my notes from that browser session on 16 May 2026, written as a companion to my talk on dark patterns. They show what I found in that session; they don’t tell us what every visitor receives or what happens to the data afterwards.

## Reproducing the observation

In a Chromium browser, I opened the developer tools on `linkedin.com/feed` and inspected requests to extension resources. Failed requests included:

```
GET chrome-extension://invalid/   net::ERR_FAILED
GET chrome-extension://<32-char-id>/<some-file>   net::ERR_FAILED
```

Following a request’s **Initiator** led to the code making the probe. A failed request alone is not proof of a particular extension being installed. The interesting evidence is the combination of the resource list, the probing function, and what it does with resolved requests.

The loop reads `{ id, file }` entries and calls `fetch()` on a `chrome-extension://` URL. Resolved fetches add an ID to a results array. An optional delay spaces out requests. Two predicates, `a()` and `s()`, determine whether the function runs; their meaning is not established by this excerpt.

When the results array is non-empty, the code calls `fireTrackingPayload()` with an event named `AedEvent` and a `browserExtensionIds` field. This shows how the function packages detected identifiers. It does not, by itself, explain the subsequent processing or retention of those identifiers.

Each entry pairs an extension ID with a resource path. A file path can become stale when an extension changes, so a failed probe is not conclusive evidence that an extension is absent.

## Testing one listed extension

I selected a listed distraction-blocking extension, installed it, and refreshed the feed. The corresponding resource request then resolved where it had previously failed:

```
chrome-extension://ppdjgkniggbikifojmkindmbhppmoell/icons/icon128.png
```

The initiator chain returned to the same probing function in a LinkedIn asset bundle. That change supported the interpretation that the code was testing whether a known extension resource was reachable.

The mechanism depends on the extension exposing a resource to the requesting page. Chrome extensions can declare `web_accessible_resources`, with rules controlling which origins can load them. Browser behaviour, the manifest, the allowed origins, and the resource path all matter.

[Chrome’s documentation on web-accessible resources](https://developer.chrome.com/docs/extensions/reference/manifest/web-accessible-resources) explains those rules. The probe uses resource requests rather than the permission-gated `chrome.management` API.

## What the evidence supports

- The inspected bundle contains a conditional function that probes known extension resource URLs.
- It packages identifiers from resolved requests into an `AedEvent` payload.
- Installing one listed extension changed the observed response to its resource probe.
- A separate sensor assembled browser and device properties in the same session.

Those observations are narrower than a claim about all LinkedIn users, all browser extensions, or every use of the resulting data. Browser code changes, so a later reproduction may differ.

The code excerpts and payload above are retained from my original inspection. They are presented as evidence to examine, rather than code to run on another person’s browser.
